## 1. How PaRSEC represents and unfolds a DAG it never builds

### 1.1 PTG: a task class is a set of functions over integer parameters

A PTG taskpool is an array of **task classes** (`task_classes_array`, P:parsec/parsec_internal.h:145).
A task is a task class plus its parameter values (`locals`). A class stores no edges. It stores
code, generated by the JDF compiler `jdf2c`:

| field (P:parsec/parsec_internal.h) | role |
|---|---|
| `params[]`, `locals[]` (:424-425) | the parameter space: ranges, possibly depending on earlier parameters |
| `in[]` / `out[]` flows with `dep_in`/`dep_out` (:426-427) | symbolic dependencies: guarded calls `cond ? Class(f(params))` |
| `dependencies_goal` (:423) | the in-degree, when it does not depend on the instance |
| `priority` (:428) | a priority expression over the parameters |
| `make_key` (:435) | collision-free key from the parameters |
| `find_deps` / `update_deps` (:449-450) | where the instance's counter lives, and how it is decremented |
| `iterate_successors` / `iterate_predecessors` (:452-453) | generated loops that **compute** neighbours from the parameters |
| `release_deps` (:454) | on completion: iterate successors, decrement their counters, schedule the ready ones |
| `time_estimate` (:443) | per-device time estimate, used for device choice (§3.6) |

**Successors are computed, not stored.** `jdf_generate_code_iterate_successors_or_predecessors`
(P:parsec/interfaces/ptg/ptg-compiler/jdf2c.c:7672-8056) emits one block per flow and per
dependency. A guard becomes an `if` (:7930-8012). A range argument becomes a `for` loop over
the target's parameter (:7510-7522). Each candidate is checked against the target's execution space
(:7529-7548). Then the code computes the successor's priority (:7576-7583) and calls `ontask(...)`
on a stack-allocated task `nc` (:7376-7381, :7878-7882). On completion,
`release_deps_of_<class>` calls `iterate_successors(..., parsec_release_dep_fct, &arg)`
(jdf2c.c:7273-7275). `parsec_release_dep_fct` (P:parsec/parsec.c:1848-1987) calls
`parsec_release_local_OUT_dependencies` (parsec.c:1761-1846). That function finds the successor's
counter (`find_deps`, :1782) and decrements it (`update_deps`, :1784). Only when the counter
reaches its goal does it allocate a real task object (`parsec_thread_mempool_allocate`, :1796) and
insert it into a ready ring sorted by priority (`parsec_list_item_ring_push_sorted`, :1835-1838).
The rings are then handed to the scheduler (`__parsec_schedule_vp`, jdf2c.c:7300-7301).
**A task object exists only from readiness to completion.**

**Dependency counters are lazy and keyed by parameters.** There are two storage modes, chosen at
compile time (`--dep-management`, P:parsec/interfaces/ptg/ptg-compiler/main.c:56,282-285). The
default is the hash table.

- **Dynamic hash table (default).** `parsec_hash_find_deps` (parsec.c:1592-1619) looks up
  `make_key(locals)`. On a miss it inserts a zeroed `parsec_hashable_dependency_t`
  (parsec_internal.h:232-237): a hash item plus one `int32` counter. A counter therefore exists
  only once a task has **at least one satisfied input**. It is freed in the generated
  `release_task` (jdf2c.c:4022-4041), which runs when the task completes. Live counter state is
  "partially satisfied, ready or running" tasks, never the whole space.
- **Index array.** `parsec_default_find_deps` (parsec.c:1570-1590) walks a nested array, one
  level per parameter, sized by each parameter's `[min, max]`. The array is allocated by scanning
  the execution space at init (`ALLOCATE_DEP_TRACKING`, jdf2c.c:3692-3730). It is dense but has
  no hashing.

The **goal is computed on the first decrement.** In `parsec_update_deps_with_counter`
(parsec.c:1621-1666), if the counter is 0 the code computes the goal from the symbolic in-deps
(`parsec_check_IN_dependencies_with_counter`, :1483-1568), subtracts 1, and CASes it in. Otherwise
it atomically decrements. The task is ready when the count reaches 0 (:1665). The goal is either a
compile-time constant (`dependencies_goal`, :1493-1499) or evaluated per instance from the guards.
A control-gather count can be an expression (`ctl_gather_nb`, :1523-1528). In the hard case the
goal is counted by running `iterate_predecessors` (:1531-1532). There is also a bitmask variant
(`parsec_update_deps_with_mask`, :1668-1732): one bit per input flow, used by classes with
`PARSEC_USE_DEPS_MASK`.

**Keys are mixed-radix encodings of the parameters.** The generated `make_key` is
`Σ (p_i − min_i) · Π_{j<i} range_j` (jdf2c.c:4877-4912). The `min` and `range` values come from
the init scan (jdf2c.c:3772-3786). This is exactly our `SIG_BASE + offsets[k] + i` scheme
(S:src/sim/whole.rs:535-546).

**Startup tasks come from a resumable scan.** For each class that can be a startup task, the
generated startup function iterates the class's whole execution space. It keeps tasks whose inputs
are all direct memory reads (`jdf_generate_direct_input_conditions`, jdf2c.c:3163), marks them
started (`parsec_dependencies_mark_task_as_startup`, parsec.c:1742-1754), and pushes them sorted by
priority (jdf2c.c:3244-3248). It hands out batches of geometrically growing size, up to
`parsec_task_startup_iter` = 64. It yields with `PARSEC_HOOK_RETURN_AGAIN` after
`parsec_task_startup_chunk` = 256 tasks (jdf2c.c:3249-3267; defaults at parsec.c:80-81) and
resumes from saved loop indices (the `restore_context_N` labels, :3080-3087 and :3124-3145). The
whole space is also scanned once at init to count tasks for termination (`nb_tasks++`,
jdf2c.c:3659-3661, :3764-3770). That is O(space), but each task costs only a few integer operations.

**Priorities are expressions, evaluated once.** The JDF grammar puts `; expr` after the dataflow
(P:parsec/interfaces/ptg/ptg-compiler/parsec.y:978-983). Example: `prio = %{ ... (NJ*NK*i + NK*j +
k)*pri %}` then `; prio` (P:tests/dsl/ptg/startup.jdf:41,48). A task's priority is
`taskpool->priority + priority_of_<class>(locals)`. It is computed when the successor is discovered
(jdf2c.c:7576-7583) or at startup (:3211-3216), and never recomputed. Larger is more urgent
(`HIGHER_IS_BETTER`, P:parsec/include/parsec/parsec_config_bottom.h:172-176). The taskpool term
is a per-pool offset (`parsec_taskpool_set_priority`, parsec.c:2124-2130), i.e. a group priority.

**Termination comes from counts, not graph state.** A taskpool carries `nb_tasks`, the count of
tasks known from the init scan, and `nb_pending_actions`, which holds +1 while `nb_tasks > 0` plus
any in-flight runtime actions (parsec_internal.h:121-141). The `local` termdet module declares
termination when its monitor is BUSY and `nb_pending_actions` reaches 0
(P:parsec/mca/termdet/local/termdet_local_module.c:156-172, :218-258). It then calls the
taskpool's `on_complete` callback (P:parsec/scheduling.c:231-238). `user-triggered` and
`dynamic` modes exist for unknown counts (jdf.h:205-210). `fourcounter` is the distributed one
(P:parsec/mca/termdet/fourcounter/, opened by `parsec_termdet_open_dyn_module`,
P:parsec/termdet.c:104-108). Many taskpools can be active in one context, each with its own
termination (`parsec_context_add_taskpool`, scheduling.c:901-963). A "compound" chains taskpools
by enabling the next in the previous one's `on_complete` (P:parsec/compound.c:21-37).

**Limitation.** With hash deps, completed tasks leave no trace. `parsec_hash_find_deps` returns
NULL for debugging lookups (parsec.c:1601-1605), so the debug enumerator cannot classify them
(parsec.c:2836-2842). Completion is known only in aggregate, through the counts.

### 1.2 DTD: an explicit graph, bounded by an insertion window

DTD discovers edges from the order of data accesses. Each tile keeps `last_user` and
`last_writer` (P:parsec/interfaces/dtd/insert_function_internal.h:180-198). A task starts with
`flow_count = nb_flows + 1` (insert_function.c:2840). The count is decremented as flows are
satisfied, and the task is scheduled when it hits zero (`parsec_dtd_schedule_task_if_ready`,
:2958-2973). The graph is explicit, like our `DagScheduler`. It is bounded by **throttling
insertion**:

- `task_window_size` starts at **1** (insert_function.c:1560). Every insertion increments
  `local_task_inserted`. When the count reaches a multiple of the window, the window doubles until
  it reaches `parsec_dtd_window_size` = 8000. From then on, every multiple of the window makes the
  inserting thread block (`parsec_dtd_record_local_task_inserted`, :2975-2992). This is a TCP-like
  slow start.
- Blocking means **the producer turns worker**. `parsec_execute_and_come_back` (:689-736) runs
  tasks from the scheduler while `tp->nb_tasks > parsec_dtd_threshold_size` (= 4000, :76) and
  returns once the count falls to the threshold (:3306-3308). The check happens only every
  `window` insertions, so in-flight tasks oscillate between about the threshold and
  threshold + window: a hysteresis band of [4000, ~12000].
- The doc comment says both defaults are 2048 (:575-582); the code says 8000/4000 (:75-76). The
  doc is stale. P:docs/doxygen/dtd.md:360-364 describes the parameters as "how long the producer
  keeps inserting before helping the workers".

The window **throttles discovery, never execution**: tasks already inserted run freely.

## 2. What to extract into `sched`'s DAG layer

How our layer works today. `declare_template` expands a whole template into petgraph nodes and
edges (S:src/dag.rs:723-743). It runs a cycle check over the batch (:860) and rank propagation
per node (:864-872). Each node carries a full `JobSpec` (:282-295). Completed ids go into a
`HashSet` forever (:357, :668-670) unless `forget_completed_below` is used (:437-442). That needs
ids allocated in completion order, which the whole-run id scheme does not satisfy (ids are
`4k+r` and `SIG_BASE+offset+i`, S:src/sim/whole.rs:535-546), and `whole.rs` never calls it. The
whole run therefore remembers about 4.1M completed ids in `completed`.

### E1. Implicit successors: a template instance holds counters, not nodes or edges (PTG `iterate_successors` + hash deps)

- **Extract.** An open group stores `(template, base id, per-node counters, remaining sinks)`.
  Successors come from the shared `DagTemplate::successors` (S:src/dag.rs:128-131), which is
  already the "generated successor function". Counters are `u16` (A(4) has 32,768 nodes, so the
  in-degree is below 2^16). A node's counter is the template in-degree `pred[i].len()`, copied
  when the instance opens; PaRSEC's lazy first-touch init (parsec.c:1639-1646) is an alternative.
  The `JobSpec` is built only when the node becomes ready, through a caller-supplied factory.
  PaRSEC likewise allocates the task object only on readiness (parsec.c:1796).
- **Dense vs lazy counters.** Dense costs 2 B × template length per open instance: 64 KiB for
  A(4). About 280 open instances at the uncapped peak (S:RESULTS.md, "Removing the caps") is
  roughly 18 MiB. A lazy hash, like PaRSEC's, stores only touched nodes at about 16-24 B each. It
  wins only when instances are huge and touched sparsely. Signature walks touch every node, so
  **use dense**.
- **Compared with today.** Today each instance node costs a `Node` (≈150 B: a `JobSpec` with three
  `Vec`/`Option<String>` fields, plus `unmet`, `work` and `rank`). The `index` HashMap entry adds
  ≈32 B. The `prefer` heap copy that `whole.rs` makes for every job (S:src/sim/whole.rs:989-993)
  adds 56 B. Each edge is a petgraph record of ≈16-24 B. An A(4) instance (32,768 nodes, 195,579
  edges) is therefore about 13 MB, against 64 KiB implicit. These are byte estimates from the
  struct layouts, not measurements. The RESULTS peak of 490k live nodes is ≈100-150 MB today and
  a few MB implicit.
- **Time.** Opening an instance costs O(n) (a memcpy of counters) instead of O(n + E) petgraph
  inserts, the batch DFS cycle check and per-node rank propagation. Completing a node costs
  O(out-degree), as today. **Unmeasured.** Profile the declare path in `sched-whole` (each plan
  simulates in about 8 minutes) before claiming a wall-time gain.

### E2. Completion is implied by group state; no per-task completed set (PTG `release_task` frees the counter)

- **Extract.** Inside an open instance, "completed" is a sentinel counter value (`u16::MAX`).
  Outside, it is "group done". Group completion is O(groups) state: a bitset of 81k bits ≈ 10 KiB,
  or a `completed_floor` per row if rows finish in order. This removes the unbounded `completed`
  set.
- **Caveat.** PaRSEC loses per-task introspection this way (parsec.c:1601-1605). We keep it,
  because the dense counters of open instances remain. Only closed instances collapse to one bit.

### E3. The goal as a closed form, with gathers as counts (`dependencies_goal`, `ctl_gather_nb`)

- **Extract.** A "walk done" join over the template's sinks is just a counter
  `remaining_sinks = |sinks|`, decremented when a sink completes. No passthrough node or edges are
  needed. This replaces the `done_deps` vector (S:src/sim/whole.rs:1045, 1065-1070). The group's
  entry (the zero step) is the instance's precondition: open an instance when its entry completes,
  and its sources are ready at once. This matches PaRSEC's startup tasks, minus the scan.

### E4. Priorities as functions evaluated at discovery (`priority` expression + taskpool priority)

- **Extract.** Add `fn priority(&self, group, node) -> Option<i64>` on the factory. It is
  evaluated once, when the node becomes ready, and frozen (jdf2c.c:7576-7583). The group term
  maps to our engine's existing `Key { priority, group, seq }` (S:src/engine.rs, `Key`).
- **Ranks.** If wanted, compute per-instance bottom levels when the instance opens, in O(E) per
  instance, by exposing the `below` vector that `DagTemplate::critical_path` already computes
  (S:src/dag.rs:187-200). Do not propagate ranks through a live graph.
- **Evidence and scope.** This matches the finding that rank ordering did not beat oldest group
  first (S:RESULTS.md, "Ordering"). Expressions keep the cheap path and leave room for
  experiments. The rank-propagation code (`propagate_rank`, `update_work`) stays for the explicit
  layer only.

### E5. A discovery window as the frontier budget (DTD window + threshold + slow start)

- **Extract.** Add an optional budget on **open instances**, not on ready or running jobs. When a
  group's entry completes and `live_instance_cost + cost(g) > high_water`, queue the group in
  `pending_open`, ordered by group priority. Open queued groups whenever the live cost falls to
  `low_water`; this is the DTD threshold (insert_function.c:716). Slow start (window 1 → ×2,
  :2982-2985) is not needed: our cost is known at expansion.
- **Why it is principled.** The DTD window bounds memory, not concurrency. A budget only on
  discovered state, sized so that ready work never runs dry, is the PaRSEC answer to the
  "≤ 24 open bidegrees" cap. That cap cost 16-21% (S:RESULTS.md, "Removing the caps") because it
  starved execution, and it was set by hand.
- **Default.** Default it to `None`. With E1 the uncapped peak is a few MB.
- **Escape hatch.** At least one instance is always openable, like `running == 0` in admission
  (S:README.md:71-76). Open queued groups in group-arrival order. An open instance's progress never
  depends on an unopened group: cross-group edges reach only zero steps, which are outside
  instances. So this cannot deadlock.

### E6. Termination and stall detection from counts (`nb_tasks` + `nb_pending_actions`)

- **Extract.** `expected_total` (or per-group totals) is known a priori. Keep `remaining` and
  expose `is_finished()`. More valuable: a **stall check**. If `remaining > 0`, nothing is held,
  submitted or ready, and no instance has a ready node, then a completion was lost. In PaRSEC this
  is "nb_pending_actions never reaches 0" (termdet_local_module.c:164-170). Our coordinator has
  already lost runs to swallowed panics (memory: production-restart-40063109). A cheap invariant
  that names the stuck groups is worth having.

### E7. Collision-free mixed-radix ids (`make_key`)

- **Extract.** A small `IdCodec` that maps `(group, node) ↔ JobId` by
  `base[group] + node` through `partition_point`. It is already in `whole.rs`
  (S:src/sim/whole.rs:688-701). Moving it into the library makes the implicit layer
  self-contained: it must map an id back to its instance on `completed`.

### Proposed API (new; nothing here exists yet)

```rust
/// Builds the job for a template node when it becomes ready (PaRSEC builds the task object only then).
pub trait NodeFactory {
    /// The job for node `node` of group `group`'s instance. `deps` is ignored.
    fn node(&self, group: u64, node: usize) -> DagJob;
    /// A priority evaluated once at readiness; `None` defers to the policy's default.
    fn priority(&self, group: u64, node: usize) -> Option<i64> { None }
}

impl<P: Policy> DagScheduler<P> {
    /// Open `group` as an instance of `template` with node `i` = job `base + i`: sources are
    /// ready now, and `done` (a declared passthrough or job) completes when every sink has.
    /// Stores counters only; returns false if queued behind `DagConfig::instance_budget`.
    pub fn open_instance(&mut self, group: u64, template: Arc<DagTemplate>, base: JobId,
                         done: JobId, cost: f64, factory: &dyn NodeFactory, now: Instant) -> bool;
    /// Whether every expected job has completed (needs `DagConfig::expected_total`).
    pub fn is_finished(&self) -> bool;
    /// Nothing ready, held or submitted, yet work remains: the stuck groups, for logs.
    pub fn stalled(&self) -> Option<Vec<u64>>;
}

pub struct DagConfig {           // new fields, all `serde(default)`
    /// Frontier budget on open instances' cost (high, low water); `None` = uncapped.
    pub instance_budget: Option<(f64, f64)>,
    /// Jobs (including passthroughs) the run will complete, for `is_finished`/`stalled`.
    pub expected_total: Option<u64>,
    // ...existing fields
}

impl DagTemplate {
    /// Per-node longest chain of `work` from the node to a sink (what `critical_path` maximises).
    pub fn bottom_levels(&self, work: impl Fn(usize) -> f64) -> Vec<f64>;
}
```

**Storing the factory.** The factory is passed per call (`&dyn NodeFactory`), not stored, so
`DagScheduler` stays `Clone + Debug` and serialisable. `completed()` then needs the factory too,
which is a signature change. The alternative is a generic `DagScheduler<P, F: NodeFactory = ()>`
that stores `F`. That is cleaner for callers, and the factory is rebuilt on restore. **Recommend
the generic**: `whole.rs`'s factory is a pure function of `World` and the node.

**A full `ImplicitDag` trait.** This would cover successors and in-degree for the coarse level too,
like PTG classes. It is **not recommended now**. The coarse level has 163k nodes and is cheap to
declare explicitly (S:src/sim/whole.rs:998-1020). Its forward references and placeholders already
work. Keep the hybrid: an explicit coarse level and implicit instances.

## 3. Their schedulers: what is worth emulating

All PaRSEC schedulers implement `schedule(es, ring, distance)` and `select(es, &distance)`
(P:parsec/mca/sched/sched.h:265-287). They select within one node's threads; there is no notion of
remote workers. The default is chosen by component priority: lfq 20, pbq 18, ltq 17, lhq 15,
ap/spq 12, gd 10, ll/llp 2, rnd 1, ip 0 (`*_component.c` query functions). **lfq is the
default.**

### 3.1 Algorithms, from the code

| sched | schedule | select | file:line |
|---|---|---|---|
| gd | append to a shared deque; front only if the class is `PARSEC_HIGH_PRIORITY_TASK` and distance is 0 | pop front (FIFO) | gd/sched_gd_module.c:123-169 |
| ap | merge the ring into one shared list sorted by priority | pop front (highest) | ap/sched_ap_module.c:88-115 |
| ip | sorted insert if distance is 0, else append | pop **back** (lowest priority first) | ip/sched_ip_module.c:84-113 |
| rnd | overwrite priority with `rand() + distance`, then sorted insert | pop front | rnd/sched_rnd_module.c:84-125 |
| spq | one priority-sorted list per distance, lists ordered by distance | first non-empty list, smallest distance | spq/sched_spq_module.c:131-197 |
| lfq | `hbbuffer_push_all`: fill the per-thread bounded buffer (size 4 × cores); overflow goes to the global FIFO "system queue"; a nonzero distance goes straight up | `pop_best` (highest priority) from own buffer, then neighbours' buffers in hwloc distance order, then the system queue | lfq/sched_lfq_module.c (`queue_size = vp->nb_cores * 4`), :175-213; hbbuffer.c:38-86, :222-266 |
| pbq | as lfq, but a full buffer **evicts its lowest-priority element** to the parent queue | as lfq | pbq/sched_pbq_module.c:159-198; hbbuffer.c:88-220 |
| ltq | group consecutive ready tasks that **share an input** into one max-heap; buffers hold heaps | pop best heap; on steal, split the heap in two and keep half (`heap_split_and_steal`) | ltq/sched_ltq_module.c:162-289 |
| lhq | lfq with one bounded buffer per hwloc level (size `96*(level+1)/nbcores`) | own level outward | lhq/sched_lhq_module.c:86-118, :182-220 |
| ll / llp | per-thread LIFO (llp: priority-sorted insert past `distance` elements) | own LIFO, then steal round-robin | llp/sched_llp_module.c:205-237, :304-335 |

Three runtime-wide mechanisms matter more than any single module:

### 3.2 Keep the best successor local (`parsec_runtime_keep_highest_priority_task`)

When a completion produces ready tasks, the highest-priority one goes into the completing thread's
private `next_task` slot. It bypasses the scheduler and is run next (`__parsec_schedule_vp`,
P:parsec/scheduling.c:372-438; consumed in `__parsec_get_next_task`, :602-615). This trades global
priority order for locality: the successor's inputs are hot.

- **Emulate as a soft preference.** On completion of job j on worker w, ready successors in the
  same group get `prefer = [w]` prepended. The engine honours `prefer` as a tie-break or penalty
  (S:README.md:84-89). This needs the DAG layer to learn the worker. Add
  `Policy::worker_of(job) -> Option<WorkerId>`, read before `completed`. The engine already holds
  `running[job].worker`.
- **Not testable in the simulator yet.** It has no affinity speed-up model. Do not ship without a
  measured locality benefit on workers. It may conflict with fast-first; resolve that with §3.6's
  skew rule.

### 3.3 Distance: demote work that could not run

A task whose hook returns `AGAIN` is rescheduled at `distance + 1` with its priority divided by
10, or set to lowest if 0 (P:parsec/scheduling.c:553-560, :581-588). spq serves smaller distances
first (spq:131-155). This is PaRSEC's fairness rule (sched.h:58-86).

- **Our analogue: retries** (OOM, worker loss).
- **Emulate (optional).** A `JobSpec.retries` field that enters `Key` as the leading component, so
  a repeatedly failing job cannot block healthy work at the head of the queue. Combine it with the
  existing `avoid` list.
- **Low priority.** Our engine's aging and reservations already bound waits.

### 3.4 Bounded local buffers with priority eviction (lfq/pbq)

The real content is "a small bounded per-consumer buffer in front of a global queue, evicting the
least urgent". The distributed analogue is **dispatch-ahead**: send up to k jobs per worker beyond
its free slots, to hide coordinator-to-worker latency.

- **Recall when a more urgent job arrives** (pbq's eviction, hbbuffer.c:133-170).
- **Risk.** It commits work to slow workers early, which is exactly what fast-first avoids. Only
  worth simulating if the measured coordinator gap is significant. The closed-loop sim models a
  gap (S:RESULTS.md, "Closed loop").

### 3.5 Simulator baselines worth adding

- **rnd: random priority.** Add a `Plan::Random` to `sched-whole` as the lower anchor for
  ordering. RESULTS found rank 4-7% worse than group order. A random arm shows whether ordering
  matters at all once placement is fast-first and uncapped. **Cost: about 1 hour.**
- **llp: LIFO within a group** (newest ready first). Depth-first finishes groups sooner and
  shrinks open-instance state. It is the natural companion to E5. It needs a per-group sequence
  key that sorts newest first: `seq` negated within the group's key. **About 2 hours.**
- **ltq: group affinity heaps.** Our group (bidegree) is the natural heap. "Steal half a group" is
  a placement rule with affinity. Same caveat as §3.2. **Not recommended until affinity is
  modelled.**

### 3.6 Not in `mca/sched`, but the most relevant code: `parsec_select_best_device`

This is P:parsec/mca/device/device.c:107-288, called from `__parsec_execute` (scheduling.c:141).

1. Prefer a device where an input already lives: the data's preferred or owner device
   (:177-224).
2. For every eligible device, compute `eta = device_load + time_estimate(task, dev)`. The load
   `device_load` is the sum of estimated times of tasks queued or running there: it is added at
   execute (scheduling.c:142) and removed at completion (:504-508).
3. The affinity device's eta is multiplied by `1/(1 + skew/100)`, with skew = 20% by default
   (device.c:56, :387-390, :233-238). It stays chosen unless another device beats it by more than
   20%.
4. Take the minimum eta (:246-269). CPUs are excluded unless `load_balance_allow_cpu` is set
   (:262).
5. The default `time_estimate` is `total_gflops / device_gflops` (device.c:850): relative speed.

This is greedy EFT with outstanding-work accounting and a bounded affinity bias: **"fast first",
done properly**. Our speed-aware placement was the biggest lever (−27 to −31%, S:RESULTS.md).
Fast-first currently prefers the fastest class only (S:src/sim/whole.rs:978-993).

- **Emulate as a new engine `Choice::EarliestFinish`.** Score each admitting worker by
  `wait(w) + est_work / speed(class)`, where `wait = 0` if a slot is free.
- **Optional "wait for a fast worker" rule.** Let a job hold out for a busy faster worker when
  `min_remaining(w_fast) + est/speed_fast < est/speed_slow`. This needs remaining-work estimates of
  running jobs, which the engine does not track.
- **New inputs.** `WorkerState.speed: f64` and `JobSpec.work: Option<f64>`.
- **Simulator first.** Measure it in the simulator against fast-first before any production use.
  Holding a job back breaks greedy (no idle while ready), so the W/P + D guarantee no longer
  holds.

## 4. What does not transfer, and why

- **Owner-computes and data distribution.** In PaRSEC every rank unfolds the same PTG and runs
  only tasks whose affinity data is local (`rank_of` checks, jdf2c.c:7559-7574; startup vpid
  assignment, :3165-3177; `data_affinity`, parsec_internal.h:433). Our coordinator is central and
  workers are stateless executors. Placement is a scheduling decision, not a property of the data,
  so there is no `rank_of`.
- **Communication engine and MPI.** `remote_dep*.c`, `parsec_comm_engine.c`, the
  `DISTRIBUTED` blocks in `parsec_release_dep_fct` (parsec.c:1898-1964), and `fourcounter`
  distributed termination. We have one coordinator and TCP workers, and termination is local.
- **Data repos, arenas, reshape, datatypes.** `data_repo` usage counts and reshape promises
  (jdf2c.c:7238-7322) manage tile copies between tasks. Our tasks exchange results through the
  coordinator's own storage, outside `sched`.
- **Lock-free, thread-level machinery.** `hbbuffer` CAS loops, hwloc hierarchies (lfq/lhq), and
  `es->next_task` races. `sched` is a single-threaded, deterministic event loop by design
  (S:README.md:3-7). Only the policies above transfer, not their concurrency.
- **DTD's data-access dependency inference.** `last_writer`/`last_user` per tile
  (insert_function_internal.h:180-198). Our dependencies are structural and known a priori. Only
  DTD's window idea transfers (E5).
- **JDF as a language and compiler.** We need no DSL. Rust closures and traits play the role of
  the generated functions.
- **Device chores and evaluate hooks.** Per-device incarnations (parsec_internal.h:398-404,
  device.c:130-156) correspond to our worker classes and `JobSpec.class`, which we already have.
  Only the `time_estimate` idea transfers (§3.6).

### Risks

- **Readiness order must match exactly** for the bit-identical claim in step 10. `finish` sorts
  dependents by id before releasing them (S:src/dag.rs:653-666). The instance path must do the
  same, and passthrough drains must keep worklist order (`drain_passthrough` pops from the end,
  :675-683). If exact order cannot be kept cheaply, fall back to equality as sets per event plus
  statistical equality of makespans.
- **The `rank_priority` interaction with placeholders.** The explicit layer adds `group_tail`
  (:558-593) and propagates instance ranks into the "registered" placeholder (via `update_work`,
  S:src/sim/whole.rs:1072). An implicit instance has no edges to propagate along. Restrict
  equivalence tests with `rank_priority` to cases without cross-instance rank flow, or keep the
  explicit path for rank experiments. Rank lost on this DAG anyway.
- **Cycle checking moves to template construction** (`DagTemplate::new` already rejects cycles,
  S:src/dag.rs:91-109). Cross-level cycles are impossible by construction: instances only point to
  their own `done` job. Document this invariant.
- **`cancel` semantics.** Cancelling one instance node must cancel its template descendants and
  the `done` join. Without stored edges this is a template DFS, which is fine, but the
  "orphaned forward refs" cleanup (:930-940) has no analogue. Test it explicitly.
- **Counter width.** `u16` assumes template in-degree < 65,535, which holds for A(4) (32,768
  nodes). Assert it at `open_instance`; fall back to `u32` per template if a profile ever exceeds
  it.
- **Measured gains may be small in wall time.** The simulator's 8 minutes per plan may be
  dominated by the processor-sharing model, not the DAG. Step 1 decides how much of E1 is
  worthwhile for speed. The memory and completed-set arguments hold regardless. That matters for
  a live coordinator with a long frontier, and for snapshot size (today the snapshot serialises
  the whole `completed` set, S:src/dag.rs:781-791).
