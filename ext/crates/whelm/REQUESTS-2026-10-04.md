# Requests, round 2: what `whelm` needs to replace `sched` in Nassau

From the `ext` side, 2026-10-04, after evaluating `whelm` (`e9c2e3f7b4`) against `sched` on the
whole stem-400 run (81,403 bidegrees, 4,238,157 signature tasks). This supersedes the open items
of `REQUESTS.md`, which still names `close_instance` and phase-1 APIs.

Ordered by priority. W1–W3 block the migration; W4–W9 are what we would want before calling
`whelm` the better crate; W10–W13 are release polish. Each item gives a suggested API (adapt
freely), the semantics we rely on, and what "done" means.

## Where whelm stands for us

- **Makespan: a tie once sched's rank bug is fixed.** The simulated whole run takes 3,470 h
  under `whelm` against 3,735 h under `sched` (1.02x against 1.10x the energetic bound). All of
  that comes from a bug in `sched`: it put each walk's critical-path placeholder on the
  registration node, whose row edge chained the walks of a row. With that fixed, `sched` lands at
  3,470 h on every seed. `whelm`'s unit model gets this right by construction. Keep it that way
  (see W4).
- **No gain from speculation, shadow backfill, HEFT or the exact oracle** on this workload.
- **Dispatch:** mean 14–25 µs (sched 8–9), max 2.3–3.2 ms. Fine at our scale.
- **Migrating costs us** about 1.8k lines of `ext/src/nassau/remote/dag.rs` plus the phase-1
  placer. We are willing to pay that once the gaps below are closed and the API settles.

## Blocking

### W1. Size a leaf when it is released, and again for every retry

**Why.** A signature task's host and device demand is only known when its walk reaches it (the
dimensions of the lift it builds). After a failure classed as out-of-memory, the retry must ask
for more. Today `NodeSource::spec` runs at submission, and retries reuse that spec.

**API (either shape works for us):**
```rust
impl DagScheduler<P> {
    /// Release a held leaf with its final spec; replaces what NodeSource::spec produced.
    pub fn release_with(&mut self, job: JobId, spec: JobSpec, now: Time) -> bool;
}

pub enum Input {
    // ...
    /// A failed attempt is retried with this spec instead of the previous one.
    Failed { job: JobId, attempt: Attempt, kind: FailKind, why: String, resize: Option<JobSpec> },
}
```
Or: call `NodeSource::spec` again at `release` and before each retry, passing the attempt
number and the previous failures (`&[Tried]`), so the source can grow the demand.

**Done when** an OOM retry is placed with a bigger demand, without cancelling the job and
resubmitting it (which would lose its age and attempt history).

### W2. Complete any node without running it

**Why.** Two cases:
1. **Dead inputs.** A walk finds late that a signature's inputs are all zero and completes it
   as a no-op. `NodeSource::passthrough` must answer before the node materialises, which is too
   early for us.
2. **Resume.** When we restart from a save or a walk checkpoint, bidegrees and signatures that
   are already done get marked complete, whatever state their node is in: not yet
   materialised, held-ready, waiting, or (for coarse entry/registration nodes) anything.

Today attempt-0 `Done` only completes held local nodes, and `Unit::completed` only applies at
declare time.

**API:**
```rust
impl DagScheduler<P> {
    /// Mark `job` done now, without running it. Works on leaves that are not yet materialised,
    /// held, ready, or waiting (dropped from the queue); on a running job it is `Cancel` + done.
    /// Dependents become ready as usual. Idempotent.
    pub fn complete(&mut self, job: JobId, now: Time) -> Result<(), DagError>;
}
```

**Done when** we can replace every `completed()` call in `remote/dag.rs` with it, including on
leaves of a unit that has not materialised yet.

### W3. Bound how many units are open at once

**Why.** Each open walk pins coordinator memory: its partial lifts, its thread, and its share of
the coordinator pool. `sched` enforced this with `max_open_instances` (`NASSAU_SIG_OPEN_WALKS`),
and `whelm` dropped it. Without a cap, a fully ready frontier opens about 300 walks at once.

**API:**
```rust
pub struct DagConfig {
    // ...
    /// At most this many units with started or ready leaves; the rest wait, highest rank first.
    pub max_open_units: Option<usize>,
    /// Or a budget on materialised nodes, which is closer to the memory we care about.
    pub max_live_nodes: Option<usize>,
}
```
A unit counts as open from its first `Ready` or `Start` until it completes or is `close`d. Order
the units waiting for a slot by rank (`OrderTerm::Rank`), not by declaration order.

**Done when** the open-unit count never exceeds the cap, and a unit freed by `close` lets the
next-highest-ranked unit open within the same `poll`.

## Strongly wanted

### W4. Explain a rank

**Why.** `sched`'s rank bug inflated zero-step ranks 1.38x (geometric mean) for weeks before
anyone noticed. Ranks are the whole scheduling signal; they need to be inspectable.

**API:**
```rust
pub struct RankPath {
    pub job: JobId,
    pub rank: Duration,
    /// The chain realising the rank: (node, its own work, label), from `job` to the run's end.
    pub chain: Vec<(JobId, Duration, Option<String>)>,
}
impl DagScheduler<P> {
    pub fn explain_rank(&self, job: JobId) -> Option<RankPath>;
}
```
Also add a regression test for the invariant `whelm` already holds: a unit's critical-path
estimate before materialisation contributes only along the unit's own outgoing edges, never to
a sibling that shares a successor. Our failure case: in row s, the registration of (s, t) must
not inherit the walk of (s, t+1).

### W5. A card-sharing model that saturates, used in placement

**Why.** `Sharing { k_sat, alpha }` defaults to linear and the fitted model saturates near 16
jobs per worker. Live A/B runs on our fleet saturate at 5–6 tasks per GPU (the kernels
serialise on the card). That is why we cut slots from 16 to 5 (H200) and 6 (L40S). A linear
model makes earliest-finish placement and the simulator both overrate packing.

**Asks:**
- A piecewise or tabulated throughput curve per worker class (`Sharing::Table(Vec<(u32, f64)>)`)
  alongside the power law.
- Fitting it from a `JsonlSink` log: concurrency against completion rate per class.
- Using it in `SpeedConfig`'s finish-time estimates, not only to normalise learning samples.

### W6. A pluggable cost model and batch recosting

**Why.** We price bidegrees with a fitted model (zero step on ln(tmd*nd), walk on dimensions and
subalgebra). As measured dimensions arrive, we recost thousands of pending bidegrees per pass.
Each `update_work` climbs the DAG on its own.

**API:**
```rust
pub trait CostModel: Send + Sync {
    fn estimate(&self, unit: JobId) -> Option<Duration>;
}
impl DagScheduler<P> {
    /// Rescale many units, then re-rank once. Changes under `epsilon` (relative) are skipped.
    pub fn update_work_many(&mut self, scales: &[(JobId, f64)], epsilon: f64) -> usize;
}
```

**Done when** recosting the full stem-400 region takes no longer than one `update_work` per
changed unit, measured.

### W7. Restore running attempts, don't resubmit them

**Why.** A coordinator restart loses every walk in flight, each hours long. `restore` currently
resubmits jobs that were running. We would like workers to reconnect and keep their attempts.

**API:**
```rust
pub struct RestoreOptions {
    /// Keep attempts that were running as running, on their worker, until that worker reports
    /// (Done/Failed) or fails to reconnect within `adopt_timeout`, after which they fail as
    /// LinkDied and retry.
    pub adopt_running: bool,
    pub adopt_timeout: Duration,
}
```
Our walk checkpoints restore the signature-level state on our side; we only need the scheduler
to agree about what is still running.

### W8. Tell the executor how urgent a job is

**Why.** Executors can act on urgency themselves: we give critical-path tasks a higher CUDA stream
priority (branch `kernel-priority`). The scheduler already knows each job's slack.

**API:** add `slack: Option<Duration>` (or `rank`) to `Output::Start`, or a
`fn urgency(&self, job) -> Option<Duration>` accessor that is cheap to call per start.

### W9. sched's analysis features in whelm-sim

Our `whole.rs` merge onto `whelm-sim` (local branch `whelm-eval`, uncommitted) already ports:
- the split zero-step and walk cost model (`--census-zero`, `costs.rs`);
- `--noise-sd`;
- `--segment-dims` and interpolating dims over holes.

Also wanted:
- `energy_bound` (the tight energetic lower bound) reported next to the weak one;
- the kernel-priority service model;
- replaying a production `JsonlSink` log as the workload, so policies are tuned on real
  traces.

## Release polish

### W10. Stabilise names before 0.1

Several renames landed on 2026-10-04 alone. Before releasing, keep old names for one minor
version as `#[deprecated]` aliases, refresh `REQUESTS.md`, and put `whelm-sim`'s heavy
dependencies behind a feature.

### W11. A dispatch-cost benchmark with a budget

Publish a criterion benchmark of `poll` at about 400k live nodes and 130 running jobs. Set a
target (for example mean under 25 µs, p99.9 under 1 ms), and check it in CI.

### W12. Export the DAG

`dag.export(&mut impl Write, Format::EdgeList | Format::Jsonl)` with node id, kind, work, rank,
state and label. We store dependency DAGs explicitly next to runs, and diff them across
versions.

### W13. Small API notes

- `Input::Done` with attempt 0 meaning "local job" is easy to misuse. Prefer a separate
  `Input::LocalDone(JobId)`.
- `NodeSource::work` is read several times and "must not change meanwhile". Either snapshot it
  once per unit, or say what happens when it does (debug assertion).
- `update_work(id, scale)` takes a scale, while sched's took absolute work. Taking absolute work
  (`Duration`) avoids the caller tracking base values.

---

## Who does what

Everything above is a `whelm` change; the Nassau integration (a `NodeSource` over signature
templates, the `poll`/`Output` loop, attempt bookkeeping in the walks) is ours, once W1–W3 land.
